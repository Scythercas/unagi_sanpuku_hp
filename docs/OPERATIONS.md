## 2. 資格情報の置き場所マップ

- **microCMS API キー（GET専用）** … GitHub リポジトリの Settings → Secrets（`MICROCMS_API_KEY` / `MICROCMS_SERVICE_DOMAIN`）。
- **CMS→GitHub 連携トークン（fine-grained PAT）** … microCMS の各 API の Webhook 設定内。開発者名義・**当該リポジトリ 1 つ限定**。

## 3. ビルドの起動方法

- **コード変更**：main への push で自動ビルド＆デプロイ。
- **コンテンツ更新**：ご子息が microCMS で保存（公開・更新）→ Webhook で自動再ビルド。反映まで約 1 分。
- **手動再ビルド**：GitHub の Actions タブ → 対象ワークフロー → Run workflow（`workflow_dispatch`）。トラブル時や、反映されないときに使う。

## 5. ご子息向け：更新のやり方（配布用に別途 A4 一枚化）

1. microCMS にログイン。
2. 直したい API を開く（お知らせ＝`news`、営業時間等＝`shop`、メニュー＝`menu`、写真＝`gallery`、募集＝`recruit`）。
3. 文章・写真を編集して**公開（保存）**。
4. 約 1 分でサイトに反映。反映されないときは開発者に連絡（または上記「手動再ビルド」）。
- **やってよいこと**：文章・価格・写真の差し替え、お知らせの追加、募集の ON/OFF。
- **やらないこと**：API（型）の削除・フィールドの削除・セレクト選択肢の変更。レイアウトやデザインは CMS にはなく、コード側にある。

> 注意：Hobby 無料プランには**権限制限がない**ため、ご子息のアカウントは CMS の全権限を持つ。型やフィールドを消すとビルドが落ちる。落ちても開発者が復元可能だが、上記「やらないこと」を守ること。厳密に権限を分けたくなったら有料プラン（月額）を検討。

## 6. バックアップ

- **画像**：ビルド前に取得した画像を**リポジトリにコミット**している（`src/assets/images/`）。リポジトリだけで直近の全画像を復元可能。
- **コンテンツ本文**：（任意で導入）Actions で定期的に microCMS の JSON をリポジトリへ書き出すジョブを設けると、CMS 障害・解約時もデータが残る。
- 結果として**リポジトリ＝サイトのバックアップ**。public なのでクローン/フォークで複製可能。

## 7. 引き継ぎ（案2：移管の段取り）

開発者が離脱・対応不能になる場合に備える。

1. **Transfer ownership**：GitHub のリポジトリ設定から、ご子息のアカウント（または顧客 Organization）へ移管する。移管後、Pages・Actions・Secrets の再設定が必要になる場合があるため、新担当が本書「2」「6」を見て再設定する。
2. **代替：フォーク/クローン**：連絡不能等で移管操作ができない場合も、public なのでコードは複製可能（Actions 設定・Secrets は引き継がれないため再作成する）。
3. **トークンの差し替え**：CMS→GitHub の PAT は開発者名義。新担当は自分の fine-grained PAT を発行し、microCMS の Webhook 設定を差し替える。旧トークンは失効させる。
4. **アカウントの主導権**：ドメイン・CMS・GA・GBP は顧客所有なので、開発者が抜けても顧客手元に資産が残る。リポジトリだけが開発者側なので、上記 1〜3 で回収する。

- 依存・GitHub Actions の非推奨警告（放置で将来のビルド失敗を防ぐ）。
